# Chapter 4: Simulation Foundations

## Learning Objectives

By the end of this chapter, you will be able to:

1. Understand the principles of physics simulation for robotics
2. Configure physics engines and their parameters
3. Implement sensor simulation (LiDAR, cameras, IMU)
4. Model realistic contact dynamics and friction
5. Balance simulation accuracy with computational performance
6. Apply noise models to simulate real-world sensor behavior

## 4.1 Why Simulate Robots?

**Robot simulation** provides a virtual environment to develop, test, and validate robotic systems before deploying to physical hardware.

### Benefits of Simulation

1. **Cost-effective**: No hardware damage, wear, or replacement costs
2. **Safety**: Test dangerous scenarios without risk
3. **Speed**: Iterate faster than real-time (or slower for analysis)
4. **Reproducibility**: Identical conditions for each test
5. **Scalability**: Test multiple robots simultaneously
6. **Accessibility**: Develop without physical robot access

### Limitations

1. **Reality gap**: Simulated behavior ≠ real-world behavior
2. **Computational cost**: Complex physics requires powerful hardware
3. **Model accuracy**: Approximations introduce errors
4. **Sensor realism**: Perfect sensors don't exist in reality
5. **Unforeseen interactions**: Real-world has infinite complexity

:::info The Sim-to-Real Challenge
Transferring controllers from simulation to physical robots remains an active research area. Techniques like domain randomization, system identification, and adaptive control help bridge this gap (Peng et al., 2018).
:::

## 4.2 Physics Simulation Basics

### Newton's Laws of Motion

**First Law (Inertia)**:
An object at rest stays at rest; an object in motion stays in motion unless acted upon by an external force.

**Second Law (F = ma)**:
Force equals mass times acceleration.
```
F = m × a
τ = I × α  (rotational: torque = inertia × angular acceleration)
```

**Third Law (Action-Reaction)**:
For every action, there's an equal and opposite reaction.

### Rigid Body Dynamics

A **rigid body** is an object whose shape doesn't deform. Humanoid robots are typically modeled as articulated rigid bodies connected by joints.

**State Variables**:
- **Position**: (x, y, z) in world frame
- **Orientation**: Quaternion or Euler angles
- **Linear velocity**: (vₓ, vᵧ, vᵤ)
- **Angular velocity**: (ωₓ, ωᵧ, ωᵤ)

**Equations of Motion**:
```
m × dv/dt = ΣF  (linear)
I × dω/dt = Στ  (angular)
```

Where:
- m = mass
- I = inertia tensor
- F = forces (gravity, contact, external)
- τ = torques

## 4.3 Physics Engines

### Comparison of Physics Engines

| Engine | Strengths | Weaknesses | Best For |
|--------|-----------|------------|----------|
| **ODE** | Fast, stable, open-source | Less accurate contacts | General robotics |
| **Bullet** | Good collision detection | Moderate accuracy | Mobile robots, games |
| **DART** | High accuracy, constraints | Slower | Research, humanoids |
| **Simbody** | Biomechanics, muscles | Complex API | Biomechanical systems |
| **MuJoCo** | Fast contact solver | Commercial license | Reinforcement learning |
| **PhysX** (Unity) | GPU acceleration, stable | Less customizable | Visualization, VR |

### Key Parameters

**Time Step** (`max_step_size`):
- Smaller → More accurate, slower
- Typical: 0.001s (1ms) for humanoids
- Rule: Step size < 1/(10 × highest frequency)

**Real-Time Factor** (`real_time_factor`):
- 1.0 = simulation runs at real-time speed
- &lt;1.0 = slower than real-time (more accurate)
- &gt;1.0 = faster than real-time (less accurate)

**Solver Iterations**:
- More iterations → More accurate constraint solving
- Typical: 50-200 iterations

## 4.5 Collision Detection and Response

### Collision Geometry

**Primitive Shapes** (fast):
- Box: `<box size="x y z"/>`
- Cylinder: `<cylinder radius="r" length="l"/>`
- Sphere: `<sphere radius="r"/>`

**Mesh** (accurate, slower):
```xml
<collision>
  <geometry>
    <mesh>
      <uri>model://humanoid/meshes/torso_collision.stl</uri>
    </mesh>
  </geometry>
</collision>
```

:::tip Collision Optimization
Use simplified collision geometry (primitives or low-poly meshes) for performance. Visual geometry can be detailed, but collision should be minimal.
:::

### Contact Dynamics

**Contact Model**:
When two bodies collide, the physics engine computes:
1. **Penetration depth**: How much bodies overlap
2. **Contact normal**: Direction perpendicular to contact surface
3. **Contact force**: Repulsion force to separate bodies

**Contact Parameters**:
```xml
<surface>
  <contact>
    <ode>
      <kp>1000000.0</kp>  <!-- Contact stiffness -->
      <kd>1.0</kd>          <!-- Contact damping -->
      <max_vel>0.01</max_vel>  <!-- Maximum contact correction velocity -->
      <min_depth>0.001</min_depth>  <!-- Minimum penetration for contact -->
    </ode>
  </contact>
</surface>
```

**Stiffness (`kp`)**: How hard surfaces are
- Soft: 1000-10,000
- Medium: 100,000-1,000,000
- Hard: 10,000,000+

**Damping (`kd`)**: Energy dissipation at contact
- Low: Bouncy (0.01-0.1)
- Medium: Realistic (1.0-10.0)
- High: Sticky (100+)

## 4.6 Friction

Friction opposes motion at contact surfaces.

### Friction Coefficients

**Static Friction** (`mu`):
Resistance to starting motion.

**Dynamic Friction** (`mu2`):
Resistance during motion (usually lower than static).

**Typical Values**:
- Rubber on concrete: μ = 0.7-1.0
- Metal on metal: μ = 0.15-0.3
- Ice on ice: μ = 0.02-0.1
- Teflon: μ = 0.04

### Anisotropic Friction

Different friction in different directions (e.g., tank treads):
```xml
<surface>
  <friction>
    <ode>
      <mu>0.8</mu>       <!-- Friction in primary direction -->
      <mu2>0.3</mu2>     <!-- Friction in secondary direction -->
      <fdir1>1 0 0</fdir1>  <!-- Primary friction direction -->
    </ode>
  </friction>
</surface>
```

### Example: Humanoid Foot Contact

```xml
<link name="left_foot">
  <collision name="foot_collision">
    <geometry>
      <box size="0.20 0.10 0.04"/>
    </geometry>
    <surface>
      <friction>
        <ode>
          <mu>1.0</mu>      <!-- High friction for stability -->
          <mu2>1.0</mu2>
        </ode>
      </friction>
      <contact>
        <ode>
          <kp>10000000.0</kp>  <!-- Stiff contact (concrete floor) -->
          <kd>10.0</kd>
          <max_vel>0.01</max_vel>
          <min_depth>0.001</min_depth>
        </ode>
      </contact>
    </surface>
  </collision>
</link>
```

## 4.7 Sensor Simulation

### 4.7.1 Camera Sensors

**RGB Camera**:
```xml
<sensor name="camera" type="camera">
  <camera>
    <horizontal_fov>1.047</horizontal_fov>  <!-- 60 degrees -->
    <image>
      <width>640</width>
      <height>480</height>
      <format>R8G8B8</format>
    </image>
    <clip>
      <near>0.1</near>
      <far>100.0</far>
    </clip>
    <noise>
      <type>gaussian</type>
      <mean>0.0</mean>
      <stddev>0.007</stddev>  <!-- ~2/255 noise -->
    </noise>
  </camera>
  <update_rate>30.0</update_rate>
</sensor>
```

**Depth Camera**:
```xml
<sensor name="depth_camera" type="depth">
  <camera>
    <horizontal_fov>1.047</horizontal_fov>
    <image>
      <width>640</width>
      <height>480</height>
      <format>R_FLOAT32</format>  <!-- Depth values -->
    </image>
    <clip>
      <near>0.1</near>
      <far>10.0</far>  <!-- Depth range -->
    </clip>
  </camera>
  <update_rate>30.0</update_rate>
</sensor>
```

**Camera Parameters**:
- **FOV** (Field of View): Wider = more scene, more distortion
- **Resolution**: Higher = more detail, slower processing
- **Frame rate**: 30 Hz typical, 60+ Hz for fast motion
- **Distortion**: Radial/tangential distortion models

### 4.7.2 LiDAR (LaserScan) Sensors

**2D Laser Scanner**:
```xml
<sensor name="lidar" type="ray">
  <ray>
    <scan>
      <horizontal>
        <samples>720</samples>  <!-- Number of rays -->
        <resolution>1.0</resolution>
        <min_angle>-1.57</min_angle>  <!-- -90 degrees -->
        <max_angle>1.57</max_angle>   <!-- +90 degrees -->
      </horizontal>
    </scan>
    <range>
      <min>0.10</min>  <!-- 10 cm minimum range -->
      <max>30.0</max>  <!-- 30 m maximum range -->
      <resolution>0.01</resolution>  <!-- 1 cm resolution -->
    </range>
    <noise>
      <type>gaussian</type>
      <mean>0.0</mean>
      <stddev>0.01</stddev>  <!-- 1 cm noise -->
    </noise>
  </ray>
  <update_rate>10.0</update_rate>
</sensor>
```

**3D LiDAR (Velodyne-style)**:
```xml
<sensor name="velodyne" type="ray">
  <ray>
    <scan>
      <horizontal>
        <samples>1800</samples>  <!-- 0.2° resolution -->
        <min_angle>-3.14159</min_angle>
        <max_angle>3.14159</max_angle>
      </horizontal>
      <vertical>
        <samples>16</samples>  <!-- 16 layers (VLP-16) -->
        <min_angle>-0.2618</min_angle>  <!-- -15° -->
        <max_angle>0.2618</max_angle>   <!-- +15° -->
      </vertical>
    </scan>
    <range>
      <min>0.5</min>
      <max>100.0</max>
    </range>
  </ray>
  <update_rate>10.0</update_rate>
</sensor>
```

### 4.7.3 IMU (Inertial Measurement Unit)

**IMU Configuration**:
```xml
<sensor name="imu" type="imu">
  <imu>
    <angular_velocity>
      <x>
        <noise type="gaussian">
          <mean>0.0</mean>
          <stddev>0.009</stddev>  <!-- Gyroscope noise -->
          <bias_mean>0.00075</bias_mean>
          <bias_stddev>0.0000008</bias_stddev>
        </noise>
      </x>
      <y>
        <noise type="gaussian">
          <mean>0.0</mean>
          <stddev>0.009</stddev>
        </noise>
      </y>
      <z>
        <noise type="gaussian">
          <mean>0.0</mean>
          <stddev>0.009</stddev>
        </noise>
      </z>
    </angular_velocity>
    <linear_acceleration>
      <x>
        <noise type="gaussian">
          <mean>0.0</mean>
          <stddev>0.017</stddev>  <!-- Accelerometer noise -->
          <bias_mean>0.1</bias_mean>
          <bias_stddev>0.001</bias_stddev>
        </noise>
      </x>
      <!-- Y and Z similar -->
    </linear_acceleration>
  </imu>
  <update_rate>100.0</update_rate>  <!-- 100 Hz typical for IMU -->
</sensor>
```

**IMU Output**:
- **Orientation** (quaternion): Robot attitude
- **Angular velocity** (rad/s): Rotation rates
- **Linear acceleration** (m/s²): Accelerations (includes gravity)

## 4.8 Noise Models

### Why Add Noise?

Real sensors are imperfect:
- **Gaussian noise**: Random fluctuations
- **Bias**: Constant offset
- **Drift**: Time-varying bias
- **Quantization**: Discrete steps (e.g., 12-bit ADC)

### Gaussian Noise

```xml
<noise>
  <type>gaussian</type>
  <mean>0.0</mean>        <!-- Average offset -->
  <stddev>0.01</stddev>   <!-- Standard deviation -->
</noise>
```

**Effect**: ~68% of readings within ±1σ, ~95% within ±2σ

### Bias and Drift

```xml
<noise type="gaussian">
  <mean>0.0</mean>
  <stddev>0.01</stddev>
  <bias_mean>0.05</bias_mean>         <!-- Constant bias -->
  <bias_stddev>0.001</bias_stddev>    <!-- Bias variation -->
  <dynamic_bias_stddev>0.0001</dynamic_bias_stddev>  <!-- Drift -->
  <dynamic_bias_correlation_time>1000.0</dynamic_bias_correlation_time>
</noise>
```

## 4.9 Performance vs. Accuracy Trade-offs

### Factors Affecting Performance

1. **Physics step size**: Smaller = more accurate, slower
2. **Collision complexity**: Meshes vs. primitives
3. **Contact solver iterations**: More = accurate contacts, slower
4. **Number of bodies**: Each link adds computation
5. **Sensor ray count**: LiDAR with 1000 rays > 100 rays

### Optimization Strategies

**1. Simplify Collision Geometry**:
```xml
<!-- Visual: Detailed -->
<visual>
  <geometry>
    <mesh><uri>detailed_model.dae</uri></mesh>
  </geometry>
</visual>

<!-- Collision: Simple -->
<collision>
  <geometry>
    <box size="0.3 0.2 0.4"/>
  </geometry>
</collision>
```

**2. Adjust Update Rates**:
- Camera: 30 Hz (adequate for most tasks)
- LiDAR: 10 Hz (static environments)
- IMU: 100 Hz (control feedback)
- Physics: 1000 Hz (0.001s step)

**3. Use Appropriate Physics Engine**:
- Fast prototyping: ODE
- Accurate humanoids: DART
- RL training: MuJoCo

**4. Disable Unnecessary Features**:
- Self-collisions (if not needed)
- Shadow rendering
- Unused sensors

## 4.10 Simulation Best Practices

### 1. Start Simple, Add Complexity

Begin with:
- Basic geometry (boxes, cylinders)
- Simple physics (ODE, large time step)
- No noise on sensors

Then add:
- Detailed meshes
- Accurate physics parameters
- Sensor noise
- Complex environments

### 2. Validate Against Reality

**Sim-to-Real Validation**:
1. Measure real robot properties (mass, inertia, friction)
2. Configure simulation to match
3. Run identical experiments in sim and reality
4. Compare results, tune parameters

### 3. Use Domain Randomization

Vary parameters to improve robustness:
- Mass: ±10%
- Friction: ±20%
- Sensor noise: ±50%
- External forces: Random perturbations

### 4. Monitor Performance

```python
# Check real-time factor
real_time_factor = simulation_time / wall_clock_time

if real_time_factor < 0.5:
    print("Warning: Simulation running slow!")
    # Consider simplifying model or increasing step size
```
